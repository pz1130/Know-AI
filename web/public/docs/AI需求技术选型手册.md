# AI 需求技术选型手册（多边开发银行版）

给谁用：方案架构师。业务局送来一个需求时，用这份文档判断该做成什么形态、需要哪些组件、选什么产品。

怎么用，按情况挑一个入口：

- 需求已经说清楚，走第二章的分诊决策树。五个问题定形态，再翻第三章看该形态的组件与产品。
- 需求含糊，或者听着像以前见过，先翻第六章的场景对照库，找相似的需求原话。
- 拿不准，或者要写立项与评审材料，用第五章的属性打分表。七个维度打完分，按组合读结论。

两个前提写在前面。一是假设技术底座基本从零开始，所以第七章给了建设顺序。二是本行的合规、保密与问责要求高于一般企业，第四章有一节专门讲这类硬约束，任何形态都不能绕过。

---

# 一、先破一个误区

业内常把 AI 系统分成 RAG、Copilot、Workflow、Agent 四类，很多书和文章都这么写。这个分法拿来选型会出事，因为这四个词根本不在一个层面上：RAG 是一种技术手段，Copilot 是一种产品形态，Workflow 是一种流程结构，Agent 是一种自主程度。一个真实系统经常同时是这四样：Copilot 的界面、RAG 的检索、写死的流程骨架，外加个别节点让模型自己决定。所以"这个需求属于哪一类"这个问题本身就问不出答案。

这份文档改成问两件事。这个需求要输出的是信息还是动作？如果是动作，那条路径是我们事先能画出来的吗？从这两个问题出发，落到六种可交付的形态上。

---

# 二、分诊决策树

按顺序回答，中途得出结论就停。

### 问题 1：这个需求最终产出的是"信息"还是"动作"？

信息是给人看的答案、报表、草稿，人看完自己决定做什么。动作是系统真的改了什么，比如批准一笔提款、发出采购公告、更新项目风险评级、向捐助方提交报告、往贷款系统写数据。

- 输出信息，继续问题 2。
- 输出动作，跳到问题 4。
- 说不清，通常是需求方把两件事打包了。拆开做，先做信息那半。这是最常见的救项目手段。例如业务局说"做一个提款智能助手"，往往同时要查历史提款进度（信息）和自动核准附件齐全的申请（动作），两件事工期、风险、审批门完全不同，合在一起只会一起延期。

### 问题 2：答案的来源是什么？

- 来自政策文件、业务手册、评估报告、评价报告、董事会文件这类非结构化材料，属于形态 A：知识问答。
- 来自贷款系统、采购系统、财务系统、成果监测系统这类结构化数据，属于形态 B：数据问答。
- 需要产出新内容，比如起草概念说明、写督导任务报告、生成国别简报，属于形态 C：辅助生成。
- 两种来源都要，不要当一个项目做。A 和 B 的技术栈几乎没有重叠，工期和风险也完全不同，合并只会一起延期。先做一个，再考虑在上层做个路由。比如"国别简报"既要抽组合支付数据，又要引用国别战略和保障政策条款，正确拆法是 B 取数加 C 成文，分两期交付。

### 问题 3（只对 A 和 B 问）：问题的范围是封闭的还是开放的？

把用户可能问的问题类型列一列。如果能列完，而且不超过 50 种左右，这就是个封闭需求，不要上检索或 NL2SQL。做成分类路由加参数化模板，成本低一个数量级，准确率还高得多。

只有当问题类型确实列不完、用户会用各种说法问各种角度的时候，才值得上 A 或 B 的完整技术栈。

这一条被忽略的次数比想象中多。很多"智能问答"项目最后发现 80% 的流量集中在十几个问题上，比如采购限额是多少、某类合同该走哪种采购方式、某信托基金本财年还能承诺多少。这些完全可以做成参数化查询，不必上向量库。

### 问题 4：这个动作的路径，事先能画出流程图吗？

- 能画出来，分支也能穷举，属于形态 D：流程自动化。
- 画不出来，但业务域很窄（涉及的系统和接口在 10 到 15 个以内，不跨业务局），属于形态 E：限域自主 Agent。
- 画不出来，还要跨多个业务域，或者需要多路并行，属于形态 F：多 Agent 协同。先读第三章 F 节的劝退部分。

这里最容易犯的错是高估不确定性。业务局说"每个项目情况都不一样没法固定流程"，往往是因为没人认真梳理过。本行大量业务其实有成文的操作手册和审批矩阵，提款、采购、合同变更都有固定节点。先花一周让业务把流程画出来再判断，画得出来就走 D，省下的不只是钱，还有后面两年的维护和审计应对。

### 问题 5（对 D、E、F 追问）：动作可逆吗？

- 完全可逆，比如生成草稿、写临时表、建待办，可以自动执行，留回滚即可。
- 有补偿手段，比如内部台账登记可以冲正，采用自动执行，同时配补偿事务和全量审计。
- 不可逆或者对外，强制人工确认门，且必须留完整审计链路。

本行属于第三类的动作特别多，需要在需求阶段就识别出来：任何形式的资金支付与提款核准、向外部发布的采购公告与合同授予、提交董事会的文件、对外发布的数据与统计口径、制裁与廉政相关的任何判定、发给成员国政府或借款人的正式函件。这几项没有商量余地，不因为业务局嫌流程慢而放宽。

# 三、六种形态：组件与产品

每种形态给三层信息：它是什么形态、需要哪几类组件、具体可选什么产品，外加工期估算和劝退信号。

产品名单请当作起点而非结论。这个领域产品更替很快，落地前务必现查当前版本和社区活跃度，并按本行的采购与信息安全要求做合规评估。

## 形态 A：知识问答（只读 · 非结构化）

典型需求包括：把采购指南和业务手册做成能问的；历年评估报告与完工报告的检索；独立评价局历年评价发现与经验教训查询；保障政策条款咨询；董事会决议与先例查询。

必需的组件覆盖整条链路。文档解析要能处理扫描件 OCR，因为本行大量历史政策与报告是扫描 PDF。切分策略、向量库、Embedding 模型、检索与重排、大模型缺一不可。另外两项在本行都不能省：引用溯源，让答案落到具体文件的具体条款，业务人员要拿去支撑决策，说不清出处的答案没人敢用；权限过滤，文档库里混着公开文件、内部文件和董事会保密文件，检索必须在向量库层面按用户密级过滤，不能只在展示层遮挡，那等于把保密内容送进了模型上下文。

可选组件按需加。用户问得口语化时才需要查询改写；成员国语言文件较多时才需要多语言支持；只有当需求确实是"这个项目和那个信托基金是什么关系"这类关系推理时，才值得上知识图谱。

产品候选大致如下。向量库可选 Milvus、Qdrant、Weaviate，数据量不大时 pgvector 就够。Embedding 用 BGE、Conan 系列，多语言场景注意选支持成员国语言的模型。重排用 bge-reranker 或 Cohere Rerank。文档解析可用 MinerU、Unstructured、PaddleOCR。一体化平台可选 Dify、RAGFlow，也可自研。RAGFlow 取其解析与引用溯源；0.27 起界面不再提供 GraphRAG / RAPTOR，定位转向给 Agent 用的知识编译与检索底座，不要按旧按钮规划。

工期大约 2 到 6 周，不含文档整理与密级梳理。真实的时间黑洞在文档清洗和密级标注，不在技术。本行大量历史文件是扫描件、没有统一密级标签、同一政策有多个修订版本并存，这些都要先解决。

劝退时注意两类情况。文档总量不到一百篇且很少更新，直接把全文塞进上下文，别建向量库。政策文件本身有多个版本且没人能说清哪版有效，先解决文件治理，否则你只是让过期条款传播得更快；在本行引用过期采购条款是会出事的。

## 形态 B：数据问答 / DataAgent（只读 · 结构化）

典型需求包括：用说话的方式查组合数据；项目支付进度查询；"东南亚区域能源领域本财年的签约情况"；成果指标汇总；联合融资统计。

必需组件围绕"问得出、算得对、查得清"来配。数据源接入之后，语义层（口径定义）是真正的地基；其上才是 NL2SQL、SQL 执行沙箱（必须限制超时、扫描量、权限）、结果可视化和口径溯源。没有语义层，后面每一环都会把错误放大。

可选组件包括自动探索性分析、归因分析、组合异动检测，这些都建立在口径已经统一的前提上。

产品候选方面，OLAP 引擎可选 Doris、StarRocks、ClickHouse，本地或轻量场景用 DuckDB。语义层可用 Cube、MetricFlow，或者自建一套指标定义表。NL2SQL 可参考 Vanna、DB-GPT、WrenAI。

工期取决于语义层。已就绪的话 4 到 8 周；没就绪的话，先做 3 到 6 个月的口径治理。

这是六种形态里失败率最高的，而在多边开发银行尤其如此。失败原因几乎从来不是模型不行，而是没有统一口径。本行典型的口径分歧至少有这么几层：

一是金额口径。同一个"承诺额"，可能指董事会批准额、协议签署额、协议生效额，或者扣除取消后的净额，不同业务局的报表用的不是同一个。"支付额"也有累计支付、本期支付，以及是否含预付款的差别。

二是币种与汇率。本币、美元、SDR 之间怎么换，用哪一天的汇率（签署日、生效日、支付日，还是报告期末），不同系统的默认取值往往不一致，同一笔业务算出两个数很常见。

三是时间口径。财年与日历年不一致，且部分成员国的统计还按各自财年报送。

四是归属口径。区域项目怎么分摊到国别、联合融资中本行份额怎么计、技术援助算不算进组合。

五是状态口径。项目"完工"是指实物完工、账务关闭，还是完工报告已提交。

只要这些没有一个权威定义，NL2SQL 选哪个都是错的，而且错得很隐蔽：数字看起来合理，只是和财务局的口径差了 8%。如果调研时发现没有统一定义，这个需求就不是 AI 项目，是口径治理项目，要在立项材料里如实写明，不要硬接。

另外要特别注意对外风险。本行的数据经常要对外，出现在年报、开放数据门户、发展有效性回顾里。一旦 AI 生成的数字被引用到对外材料，错误就是机构声誉事件。因此这类系统的输出必须默认标注"内部参考、未经财务或统计部门确认"，并且和对外发布通道之间要有明确隔断。

劝退时注意：业务方要查的其实就固定那几张组合报表，做成参数化模板，一周搞定；源系统字段无注释、历史数据有多次迁移遗留，先补元数据。

## 形态 C：辅助生成（人在终点确认）

典型需求包括：起草项目概念说明；生成督导任务报告初稿；董事会文件摘要；国别简报；完工报告初稿；技术援助建议书初稿。

必需组件并不复杂：大模型、提示词模板与版本管理、上下文注入，以及可编辑的人工界面。本行的文件本来就要经过多级审阅，人在终点确认是现成的制度，不要为了"全自动"把它绕开。

可选组件里，检索往往是最有价值的部分，尤其是需要参考同类历史项目文件时；此外可加机构文风与模板库、多版本对比。

产品上，模型 API 加网关即可，界面自建或用 Dify 这类平台快速搭。

工期大约 1 到 3 周。

如果刚起步，第一个 AI 项目就应该做这一类。技术最简单、见效最快、风险最低，而且能帮团队建立起模型接入、提示管理、可观测、密级管理这套基本功，这些底座后面每个项目都要用。用它练手，比一上来做组合数据问答明智得多。一个常见的起步题目是"帮任务组长起草督导任务报告初稿"，价值主要来自自动带入历史督导记录和项目基础信息，而不是模型的文笔。

起草类需求虽然风险低，但涉及的输入材料密级可能很高，比如国别战略草案、董事会前的讨论稿。模型服务的部署方式、数据是否出境、供应商是否留存内容，要在第一个项目就定清楚，不要等到第三个项目才补。

## 形态 D：流程自动化（路径固定 · 会写业务数据）

典型需求包括：提款申请单据的完整性核对与录入；采购公告的分类与归档；咨询顾问简历入库与标签化；信托基金捐助方报告的数据汇总；合同要素抽取入库。

必需组件是传统集成的全套：触发器、流程编排引擎、外部系统接口封装、幂等键、重试与退避、失败告警、审计日志。少了幂等与审计，出问题后既无法安全重跑，也无法向审计委员会交代。

大模型是可选的，而且只用在个别节点。

这一节最重要的判断是：这类需求里，大模型通常只该出现在一到两个节点，比如把提款申请附件里的发票信息抽成结构化字段、把采购公告归到某个行业分类。其余环节全是传统系统集成，该写死就写死。把整条流程交给 Agent 自主决策是典型的过度设计：贵、慢、不稳定，而且出了问题没法向审计委员会复现当时的判断依据。

产品候选方面，编排引擎可选 Temporal（强在长时运行和故障恢复）、Camunda（强在有多级人工审批的业务流，与本行的审批矩阵天然契合）、n8n（轻量、集成多）、Airflow（偏数据任务）。抽取节点直接调模型 API。不要一上来就用 LangGraph 这类 Agent 框架，它们解决的是路径不确定的问题，你这里路径是确定的。

工期大约 3 到 8 周，主要花在对接内部系统。本行的贷款、采购、财务系统往往年代较久、接口有限，这部分工作量要按最悲观估计。

劝退时注意：数据来自借款国实施单位提交的材料，格式和质量不可控，先做一轮真实样本测试再报工期；需要对接的系统没有 API 只能爬界面，要评估维护成本，这类方案在审计上也很难解释。

## 形态 E：限域自主 Agent（路径不定 · 域窄）

典型需求包括：项目支付停滞原因的自动排查（跨贷款、采购、财务系统查线索）；采购投诉的初步分类与相关先例检索；某个项目保障政策合规性的自查清单生成。

四个前提条件缺一不可：工具数量可控（15 个以内）；限定在单一业务域；失败可容忍或可回滚；有明确的"算完成了"的判据。任何一条不满足，都退回形态 D 重新拆需求。

必需组件比 D 多一截。Agent 运行时要含状态持久化与断点恢复；还要工具注册与 Schema 管理、权限与凭据管理、超时与 token 预算上限、全链路追踪、人工介入点、审计日志、评测集。权限这一项尤其关键：Agent 以谁的身份访问业务系统，是继承发起人的权限还是用服务账号？在本行必须是前者，否则权限等于所有用户的并集，无法通过信息安全审查。

两处最容易低估工作量。一是工具接入。"接十个系统"要按五个动作各算一遍才是真实工作量：注册与 Schema 声明、参数校验（模型会编造参数值）、执行隔离、结果规范化、错误回传。后两项在供应商报价里经常被漏掉，但缺了它们 Agent 会在失败后重复犯同一个错。二是终止条件。Agent 靠什么停下来，要在需求阶段定成一组而不是一个：任务完成判据、最大迭代次数、超时、成本上限、置信度阈值。这就是上面四个前提里"有明确完成判据"的具体化。业务方说不出"什么情况下它该停"，项目不能启动。

产品候选方面，编排默认用 LangGraph（路径不定、要断点与审批门时）；微软栈优先 Microsoft Agent Framework（原生 MCP / A2A）。CrewAI 适合角色原型，生产环境要单独审查其代码执行沙箱。AutoGen 已进维护模式，不接新项目。另有四个 SDK 可列为备选（按所在云和模型栈挑，按下方三个硬指标的初评见表）：OpenAI Agents SDK、Google ADK、Claude Agent SDK、AWS Strands Agents。工具接入协议用 MCP（现行规范 2026-07-28 已去掉协议级会话，企业落地看 Enterprise-Managed Authorization）；追踪用 Langfuse、Phoenix；模型网关用 LiteLLM、Higress AI Gateway；沙箱用容器隔离，且白名单上的代理、共享 registry、评测夹具也算爆炸半径。

框架选型有三个硬指标，问不出明确答案就别选：能不能自动压缩上下文、用什么策略；执行状态能不能序列化和恢复、粒度多细；支不支持挂起等待外部事件（人工审批、外部回调）再继续。带审批门的流程必然中断，等人的这段时间状态必须存得住。本行提款核准、合同授予这类动作经常要等人签，框架如果存不住暂停状态，上线后会变成人工值守。

新增候选按三个硬指标的评估（版本查于 2026-10-26，来源 PyPI / npm；各项能力依据表下所列官方文档）：

## 形态 F：多 Agent 协同

典型需求包括：国别诊断类研究的资料汇总；跨部门的复杂尽调材料准备。

常见模式有扇出并行（同时派多个子任务再汇总）、流水线（依次传递）、主管—工人（一个协调多个执行）、辩论（多个独立给结论再比对）。

先看劝退。绝大多数号称需要多 Agent 的需求，其实是形态 D 或 E。多 Agent 带来的成本（协调开销、结论冲突、调试困难、token 成本失控、故障归因几乎不可能）通常远超收益。在本行还多一层问题：多 Agent 系统的决策链路很难向审计和独立评价解释清楚。

真正适合的只有两种情况：子任务确实互相独立且能并行；或者不同子任务需要完全不同的专业上下文（比如宏观经济、行业技术、保障政策），混在一个上下文里会互相干扰。除此之外都应该退回 E。

产品上，先满足形态 E 的全部要求。Agent 之间通信用 A2A；上面几个框架都自带多 Agent 编排（如 OpenAI Agents SDK 的 handoff、ADK 的多 Agent 层级、Strands 的多 Agent 模式），但 Agent 间消息必须鉴权和校验（对应 OWASP ASI07）。

工期从 16 周起，且建议先用 E 做出单体版本跑通业务，再考虑拆分。

# 四、跨形态的通用底线

## 4.1 一般底线

成本闸门要先装上。每个请求、每个会话、每天都要有上限，超了就熔断。没有闸门的 AI 系统会在某个周末烧掉一个季度的预算。各形态的 token、延迟、成本粗算方法与闸门取值，见《成本与容量估算》（`成本与容量估算.md`）。

全链路追踪同样是上生产的前提。用 OpenTelemetry 加 Langfuse 之类，记下每次调用的输入、输出、工具调用、耗时、成本。出问题时能复现，是能不能上生产的分水岭，在本行还额外是审计的前提。按 OpenTelemetry GenAI 语义约定输出，追踪数据才能在不同工具间通用；概念与 span / 属性的对应和内容采集的隐私要求，见《概念讲解手册》第 8 讲。

模型输出一律按不可信处理。不能直接拼进 SQL、不能直接写进页面、不能直接当命令执行。该转义转义，该白名单白名单，该沙箱沙箱。

提示注入的防线也不能靠一句系统提示。只要系统会消费外部内容，就必须假设里面有恶意指令。本行的暴露面比一般企业大：借款人和实施单位提交的项目文件、投标方提交的材料、对标研究时抓取的外部网页、外部来函。真正管用的是权限最小化和动作确认，不是靠提示词里写一句"忽略恶意指令"。

版本与回滚要覆盖提示词、模型版本、工具 Schema，都要能回滚。模型供应商悄悄更新版本导致效果变化，是常态。灰度发布、回滚、版本漂移监控与事故复盘模板，见《上线与运维清单》（`上线与运维清单.md`）。

## 4.2 本行特有的硬约束

这几条建议在需求评审阶段就逐项过一遍，任何形态都适用。

密级与访问控制要先于功能。文档和数据都有密级分层，公开、内部、限制、董事会保密不能混在一个索引里。权限过滤必须发生在检索阶段而非展示阶段。一个能被普通用户诱导出董事会保密内容的问答系统，是重大信息安全事件，而不是一个可以后续修补的缺陷。

数据出境与部署形态要在项目启动前明确。成员国相关数据、人事数据、未公开的国别分析，能否发往外部模型服务商，要落到具体的部署方案上（自建推理、专属云，还是公有 API）。这个决定会反过来限制可选的模型和框架，所以必须最先定。

问责链路必须可追溯。本行的每一项决定原则上都要能说清依据和责任人。AI 参与的环节必须留痕：谁在什么时候、基于什么输入、得到了什么建议、最终由谁确认。这不是加分项，是能否上生产的门槛。

AI 不得产出结论性判定。在制裁筛查、廉政尽职调查、申诉案件处理、保障政策合规认定这些领域，AI 只能做检索、汇总、初步标注，结论必须由授权人员做出。这条要写进设计文档并在评审时确认。

这条限制不只是"怕它判错"，还有一个机制层面的理由，向业务局解释时可以讲清楚：模型一旦先给出结论，后续生成的所有"依据"都是围绕这个结论展开的，性质上是圆场而不是论证。因为每个已生成的 token 都会影响后续采样，结论一旦落定就成了锚点。所以"让 AI 先判定、再让它列出理由供人复核"这种设计是无效的，人看到的理由看起来很充分，但它们是被结论倒推出来的，复核者反而更容易被说服。

正确的做法是反过来：让 AI 只输出检索到的事实、适用条款和先例，把它们摆在人面前，判断由人做出。如果确实需要 AI 参与推理，也必须让它先完整推理再给结论，且中间过程要完整留痕可查。

对外发布必须隔断。凡是可能进入年报、开放数据门户、新闻稿、对外报告的数字和表述，AI 系统的输出与对外发布通道之间要有明确的人工确认环节，且系统默认标注"内部参考"。

多语言与翻译责任也要事先讲清。涉及成员国语言时要明确：机器翻译的产物是工作参考还是正式文本。正式对外文本不能直接使用未经审校的机器翻译。

## 4.3 成本与护栏的管理面

4.1 讲的是每个系统自己要装的闸门，这一节讲平台层面怎么管。做的系统一多，单个系统的闸门就不够了，得有人从全行角度看钱花在哪、谁能叫停。

模型要分档，不要一律用最好的。我们的做法是金、银、铜三档：金档留给少量真正难的任务，比如复杂的支付停滞排查；银档是日常主力，政策问答、起草都够用；铜档干分类、字段抽取这类重复活。原则是银档能干的不上金档，铜档能干的不上银档。分档靠网关里的模型路由落地，按任务复杂度、数据密级、延迟和成本限制自动选，涉密数据只能路由到指定的自建模型，不让每个项目自己写死一家，更不让用户自己挑最贵的。

不需要秒回的活走批处理。提款单据核对、月末报表、批量分类都不急，OpenAI 的 [Batch API](https://platform.openai.com/docs/guides/batch) 和 Anthropic 的 [Message Batches](https://docs.anthropic.com/en/docs/build-with-claude/batch-processing) 都按同步价的 50% 计费（核对于 2026-10-29），代价是结果最长 24 小时返回。自建推理没有这个折扣，但能把批量任务排到夜间用闲置算力。

成本要能落到人头和部门。光有闸门熔断还不够，得能按人、团队、项目、模型看清 token 和花费，再展示给部门看（Showback）或者直接分摊到部门预算（Chargeback）。每个团队有默认额度，超了就显示多花了多少，要追加额度就写清业务价值，由业务负责人批。用的人看不到成本，就永远会挑最贵的模型。

护栏先于自主。新的 Agent 先用最小权限、工具白名单、限时访问和人工审批跑起来，评测和线上表现稳定了再一点点放权。所有能写数据或调外部系统的 Agent，都要有能一键停掉的 Kill Switch，而且要演练过：真出事时值班的人不能现找开关在哪。付款、对外承诺、改生产系统这几类动作，放权要最慢。

平台要有 Agent 台账。登记每个 Agent 的负责人、用途、模型和版本、权限范围、上线日期和计划下线日期，不然一年后没人说得清行里跑着多少个 Agent、各自能碰什么。没人认领的 Agent 按停用处理。

这一节的背景和更多做法（预算拆解、自研还是外购）见《Agent 平台落地与 AI 成本治理：会议要点》。

# 五、属性打分表

用于需求评审、立项答辩，或者决策树给不出明确答案时。七个维度各打 0 到 3 分。

| 维度 | 0 分 | 1 分 | 2 分 | 3 分 |
|---|---|---|---|---|
| **1. 决策权** | 人决定，系统只提供信息 | 系统给草稿，人确认 | 系统在写死的分支里选 | 系统运行时自己生成路径 |
| **2. 作用域** | 只读，只返回文本 | 只读，跨系统查询 | 写自己的状态/草稿 | 写业务系统或对外发出 |
| **3. 可逆性** | 完全可逆 | 有补偿手段 | 恢复困难 | 不可逆、对外、或涉及资金 |
| **4. 域宽度** | 单表单接口 | 单系统内 | 单业务域 | 跨业务局 |
| **5. 运行时长** | 秒级 | 分钟级 | 小时级 | 跨天或异步等待 |
| **6. 数据就绪度** | 已有权威口径定义 | 有数仓无统一口径 | 有库无数仓 | 数据散在各业务系统 |
| **7. 可验证性** | 有标准答案可自动比对 | 可抽检 | 只能靠人主观判断 | 产出量已超过人力审核能力 |

再加两个本行专用的判定项，不打分，只判有无：

密级触及：是否会接触到限制级以上材料。触及则权限过滤方案必须先于功能设计定稿。

问责敏感：是否落在制裁、廉政、申诉、保障政策认定这几个领域。落在其中则 AI 角色上限是资料汇总，不得产出结论。

怎么读这些分：

- 维度 2 和 3 同时 ≥2：无论其他维度如何，必须有人工确认门和完整审计。硬性。
- 维度 3 = 3 且维度 1 ≥2：涉及资金或对外，且系统自行决定动作。这个组合在本行不予通过，必须降到维度 1 ≤1（即人工确认后才执行）。
- 维度 6 ≥2 且需求属于形态 B：项目应当先转为口径治理项目，在立项材料里写明。
- 维度 7 = 3：需求不成立。产出量超过人能审核的量，意味着没人能发现它错了。先解决怎么验证。
- 维度 1 = 3 且维度 4 = 3：这是研究项目，不是交付项目。不要承诺上线时间。
- 七项总分 < 6：别上 Agent，传统方案（规则、模板、流程引擎、参数化查询）更划算也更可靠。
- 维度 5 ≥2：需要能断点续跑的编排引擎和状态持久化，直接排除大部分轻量框架。

# 六、场景对照库

按业务局常说的原话来查。

"把采购指南做成能问的"，属于形态 A。先确认哪一版指南当前有效，以及是否有针对特定融资类型的例外条款，这类例外是问答系统最容易答错的地方。

"让同事能查历年评价报告里的经验教训"，属于形态 A，而且是本行最有价值的场景之一，独立评价的知识资产长期沉淀但难以调用。注意评价报告的结论有时间和国别语境，答案必须带出处和年份，不能脱离语境引用。

"董事会文件能不能也做成能问的"，属于形态 A，但密级是硬约束。方案必须先过信息安全，权限在检索层过滤，且要能按用户所属机构和岗位区分可见范围。这个项目的难点全在权限，不在问答。

"我想直接问组合数据，不用等报表"，属于形态 B。第一句话就问"你说的承诺额是批准额、签署额还是生效额"。对方答不上或者各局不一致，转口径治理。

"做个项目组合驾驶舱，能问问题的那种"，属于形态 B。隐藏难点是响应速度和口径一致性，管理层不会等 30 秒，也不会接受和财务局的数字对不上。要提前做预计算和口径对齐。

"自动生成国别简报"，属于形态 B 加 C。取数是 B，成文是 C。分两期做，且成文部分必须走国别团队审阅。

"帮任务组长起草督导任务报告初稿"，属于形态 C。价值主要来自自动带入历史督导记录和项目基础信息，而不是模型的文笔。

"起草项目概念说明"，属于形态 C。建议把同类历史项目的检索接进去，这比单纯生成有用得多。

"贷款协议条款的风险审查"，属于形态 A 加 C。给出风险点和依据条款，结论由法律部门确认。绝不能做成自动通过。

"提款申请自动审核"，属于形态 D，且维度 3 直接满分（涉及资金、不可逆）。做法是自动做完整性和一致性核对、把疑点标出来，核准动作留给授权人员。任何"自动放款"的表述都要在需求阶段就否掉。

"供应商制裁名单自动筛查"，属于形态 D，但触发"问责敏感"判定。系统只做名单比对和相似度提示，命中与否的判定由合规部门做出。要特别注意漏报和误报的处理流程都要留痕。

"廉政尽职调查能不能自动做"，触发"问责敏感"。AI 上限是公开信息汇总和线索整理，不得产出结论或风险评级。这条要在需求阶段和业务局讲清楚，否则会一路做到验收才出问题。

"采购公告自动分类并发布"，属于形态 D。分类可以自动，发布是对外不可逆动作，必须人工确认。

"咨询顾问简历库做智能匹配"，属于形态 A 或 D，视是否要写回系统。注意个人数据保护要求，以及不能让模型输出对候选人的评价性结论。

"项目支付进度落后了，让 AI 自己去查原因"，属于形态 E，且是较适合的场景：以只读为主、失败无害、有明确完成判据（找出停滞环节）。任何写操作（改评级、发提醒函）单独拉出来做确认门。

"采购投诉来了，能不能自动初判"，属于形态 E 的检索部分可以做（找相似先例、定位适用条款），初判结论不能做，问责敏感。

"成果指标自动汇总"，属于形态 B。难点是指标定义分散在各项目的成果框架里、口径不统一、部分数据来自借款国报送且质量不可控。先评估数据可得性再谈技术。

"成员国语言的文件也要能问"，多语言场景，先拿真实文件做技术验证。要明确翻译产物的定位是工作参考还是正式文本。

"老档案的扫描件也想检索"，先用真实样本测 OCR 质量。年代久远的扫描件识别率差异极大，不能凭经验报工期。

"看看其他多边机构是怎么做的，让 AI 去调研"，消费外部网页等于直接暴露在提示注入下，工具权限必须最小化，且结果要人工核实来源。

"申诉机制的案件能不能检索相似先例"，属于形态 A，但高度敏感。涉及投诉人信息的脱敏、可见范围，以及绝不产出案件结论，这几条要先定。

"我们想做个 AI 平台，什么需求都能接"，不是需求，是愿景。要求对方给出前三个具体场景，按本文档逐个分诊，再看这三个的共同底座是什么，那才是平台第一版的范围。

"某某机构已经上线了，我们也要"，先查对方公开的是试点还是生产系统。这两者的距离通常是 10 倍工作量，主要差在权限、审计、失败恢复和成本控制上，而这几项恰恰是本行要求最高的。

"数据太多了，让 AI 帮我找组合里的异常"，这大概率是传统异常检测问题。用统计方法或机器学习成本低得多、可解释性还强，在需要向管理层解释为什么标红时这一点很关键。模型只适合把结论讲成人话。

# 七、从零开始的建设顺序

既然底座基本从零，建议按下面的顺序建，而不是按需求来的顺序建。

第 0 层最先建，做任何形态都用得上：模型接入与网关（统一 API、限流、计费、审计），提示词与版本管理，可观测（OpenTelemetry 加 Langfuse 之类），成本闸门，以及一次性把部署形态与数据出境政策定下来。这层大概两到四周，是后面所有项目的公共地基。最后那一项虽然是政策工作不是技术工作，但拖到第三个项目才定，前两个都要返工。网关要能按任务、密级和成本在多家模型之间路由，而不是每个项目写死一家。固定的系统提示和检索前缀应设计成能命中 Prefix / Prompt Cache，这是形态 A、C 最有效的成本杠杆。开源权重模型让自建推理比过去更可行，但采购、密评和供应链审查不能省。

第 1 层按方向二选一，别同时开。走知识方向，建文档处理管线、向量库，以及密级标注与权限过滤机制。走数据方向，建数仓或 OLAP，加上口径定义层。这两条路的投入差距很大。数据方向的口径治理最容易被低估，它涉及财务、业务、统计多个部门对齐定义，是组织问题不是技术问题，排期要给足，最好由一位有跨局协调权限的负责人牵头。

第 2 层要做形态 D、E 时才建：工具注册与权限管理、状态存储、编排引擎、沙箱隔离、身份传递（Agent 继承发起人权限的机制）。

第 3 层要做形态 E、F 时才建：评测体系、红队测试、细粒度成本归因、多 Agent 协调。

推荐的项目顺序如下。先用一个形态 C 的小项目（比如督导报告初稿）把第 0 层建起来，并跑通上线与安全审查流程。再做一个形态 A 的知识问答，建议从公开级文档起步，比如采购指南，把密级机制在低风险场景下先跑通。同时启动口径治理，为形态 B 铺路。最后才碰 D 和 E。

按这个顺序，团队的能力增长和风险暴露是匹配的。反过来，第一个项目就做涉及资金或董事会文件的系统，失败率很高，而且一次安全或口径事故会消耗掉机构对 AI 的耐心，这个代价比项目本身大得多。

# 八、危险信号清单

评审时听到这些话，停下来重新对齐。

业务局说不出"什么算做对了"，没有验收标准，项目不能启动。

要求"准确率 100%"，说明还没接受概率系统的本质，先做期望管理，或者改用确定性方案。

需求描述里出现"所有""任何""全自动"，范围没收敛，退回去拆。

涉及资金支付、对外发布、董事会提交、制裁或廉政判定，不可逆或问责敏感，必须有人工门，没有商量余地。

要用到限制级以上材料，但没人能说清谁该看到什么，权限方案先于功能。不要先做原型再补权限，那基本要重做。

现有流程或口径本身就是乱的：AI 不会让它变整齐，只会让分歧暴露得更快、传播得更广。先梳理。

数据依赖借款国实施单位报送，且质量不可控，先做真实样本评估，不要在方案里假设数据是干净的。

对方指着某个演示视频说"就要这个"，先确认那是不是生产系统，以及背后的数据准备和合规工作量。

没有业务局愿意当负责人，只有 IT 在推，这类项目上线后无人维护口径和知识库，半年内必然荒废。

# 九、关于原书的几点提醒

如果团队在参考《Enterprise Agent Platform Engineering》，有几处建议对照着看。

四分法不要当选型工具。原因见第一章，它的四个词不在同一层面，无法用来判断具体需求。

RAG 的定位已经变了。原书把 RAG 当成与 Agent 并列的一类系统，但业界现在普遍把它降级为"上下文工程"下面的一项技术。上下文工程要管的是检索、压缩、记忆、格式化、token 预算这一整套，比 RAG 大得多。

缺三个重要维度。原书的框架没有涵盖：多 Agent 的组织形态（谁监督谁、冲突怎么办）、长时运行与中断恢复、爆炸半径（沙箱里跑还是握着生产系统凭据跑）。这三样在实际选型中的权重都很高。

合规部分偏通用。原书的安全合规章节以一般企业和通用法规为主，对国际组织特有的问题着墨不多：豁免地位下的适用法律、成员国数据主权、董事会保密分级、独立评价与审计的可追溯要求、问责机制。这些需要本行自己补，本文档第 4.2 节是个起点。

产品清单会过时。原书列的框架和产品需要按当前时点重新核实，尤其推理引擎和 Agent 框架更替很快，且要叠加本行的采购与信息安全要求。

口径治理的分量被讲得不够重。原书在数据基础设施上着墨很多，但没有足够强调：数据问答类项目的成败几乎完全取决于口径定义是否存在，这应该是立项时的一票否决项。

风险分层那部分值得单独提炼。原书第一部分第 2 章关于低中高风险分层的内容，是全书定义部分最实用的，可以和本文档第五章的打分表结合起来用。
