# 概念层级图谱：从 LLM 到 Agent

把原书的概念按"从底往上一层层加能力"的顺序重新排。这个顺序同时也是历史顺序——每一层都是当年为了解决上一层的局限而加出来的。

**核心认知先说在前面：这些层不是互相取代，是叠加。** 今天一个生产 Agent 系统里，从 L0 到 L5 全都同时在跑。所以理解每层解决了什么、又留下了什么问题，比记住术语重要得多。

```
L6  多 Agent 协同        A2A、Agent Card、扇出/流水线/主管-工人
     ↑ 一个不够用了
L5  Agent（循环）        ReAct、Runtime、记忆、状态恢复、HITL
     ↑ 一次调用不够用了
L4  标准化工具接入        MCP、工具注册中心、Schema 版本
     ↑ 每个系统单独对接太贵
L3  函数调用（动手）      Function Calling、Tool Use、JSON Schema
     ↑ 只能说不能做
L2  上下文供给（知道）    ┌─ 非结构化：向量库、检索、重排  → 知识问答
                          └─ 结构化：CDC、湖仓、OLAP、语义层 → 数据问答
     ↑ 不知道企业内部的事
L1  对话（记住这一轮）    上下文窗口、提示工程、CoT
     ↑ 无状态、一问一答
L0  模型本身              Transformer、KV Cache、量化、微调

横切所有层：可观测、评测、安全、成本、部署
```

---

# L0 · 模型本身

**这一层是什么**：一个"给一段文本、出一段文本"的函数。仅此而已。它没有记忆、不联网、不会动手、也不知道现在几点。

**书里对应的概念**：LLM、Transformer、自回归生成；推理侧的 KV Cache、Prefix Cache、投机解码、量化（GPTQ/AWQ 等）；适配侧的微调、LoRA、DPO；推理引擎 vLLM、SGLang、LMDeploy。

**要建立的关键认知**：模型参数里的知识是训练时冻结的，有明确的截止日期，而且它不"知道"自己不知道什么——不确定的时候它会给出一个流畅且自信的错误答案。这不是缺陷可以修，是这类模型的工作方式。后面所有层，某种意义上都是在给这个事实打补丁。

**这一层引入的故障模式**：编造（一本正经地给出不存在的条款和数字）、知识过期、算术不可靠。

**我们的实际选择**：这一层的大部分优化细节（推理引擎、量化、KV 缓存）只有自建 GPU 集群才需要深入。用 API 或托管服务的话，了解概念、知道成本和延迟从哪来即可。

---

# L1 · 对话

**这一层解决什么**：把上面那个无状态的函数包装成看起来能连续交流的东西。这就是 2022 年底 ChatGPT 引爆的那一步——技术上不是新模型能力，是交互形态的发明。

**书里对应的概念**：上下文窗口、token 预算、提示工程、CoT（思维链）、ToT（思维树）、系统提示。

**要建立的关键认知**：**多轮对话是幻觉。** 模型本身根本不记得上一句话，是应用层每一轮都把之前的全部历史重新发一遍，模型才"显得"记得。这带来两个直接后果：一是对话越长越贵，因为每轮都在为整段历史付费；二是历史超过窗口就必须截断或压缩，而怎么截断直接决定体验好坏。

**这一层引入的故障模式**：上下文溢出导致的"失忆"、长对话中的信息稀释（相关内容埋在中间时准确率下降）、成本随对话长度线性甚至更快增长。

**对应我们的形态**：形态 C（辅助生成）基本只需要到这一层，这也是它工期最短、风险最低的原因。

---

# L2 · 上下文供给

**这一层解决什么**：模型不知道我们机构内部的任何事。所以在提问的时候，把相关资料一起塞给它。

这一层要分成两条完全不同的技术路线，这个分叉在原书里没有讲得足够清楚，但对我们的选型影响极大。

## L2-A 非结构化：知识问答

**书里对应的概念**：Embedding、向量库、稠密检索、稀疏检索（BM25）、混合检索、RRF、HNSW/IVF/PQ、重排器、Cross-Encoder、ColBERT、切分策略、OCR、文档解析、GraphRAG、知识图谱。

**要建立的关键认知**：RAG 不是让模型变聪明，是在提问时把参考资料递过去。所以答案质量的上限由检索质量决定，不由模型决定——检索没找到，模型再强也答不对，而且往往会用参数里的旧知识硬答。

另外，**这个词的地位已经变了**。业界现在把 RAG 降级为"上下文工程"里的一项技术。上下文工程管的是整件事：检索什么、压缩什么、记住什么、怎么排版、token 预算怎么分。检索只是其中一环。

## L2-B 结构化：数据问答

**书里对应的概念**：CDC、WAL、ELT、湖仓（Iceberg/Hudi/Delta/Paimon）、OLAP（Doris/StarRocks/ClickHouse/DuckDB）、MPP、语义层、Headless BI、NL2SQL、Schema Linking、数据目录、血缘、数据契约、质量门禁、流处理（Kafka/Flink/Watermark/Checkpoint）。

**要建立的关键认知**：这条线的重量级远超另一条。它不是"给模型接个数据库"，而是要先有干净的数仓和统一的口径定义，模型才有东西可查。原书用了整整几个部分讲数据基础设施，就是这个原因。

**这一层引入的故障模式**：检索不到（切分不当、查询表述与文档用词不匹配）、检索到过期或失效的版本、口径不一致导致数字看着合理但是错的、权限过滤失效导致越权可见。

**对应我们的形态**：L2-A 对应形态 A，L2-B 对应形态 B。这也是为什么选型手册里反复说这两个不要合成一个项目——它们只在最上面那层调用模型时相同，往下几乎没有共享。

---

# L3 · 函数调用

**这一层解决什么**：前面两层做完，系统仍然只能"说"，不能"做"。函数调用让模型能表达"我想调用某个工具、参数是这些"。

**书里对应的概念**：Function Calling、Tool Use、JSON Schema、结构化输出。

**要建立的关键认知，这是整份文档最重要的一条**：**模型不执行任何东西。** 它输出的只是一段结构化文本，意思是"我建议调用 X，参数是 Y"。真正去调用的是我们自己写的宿主程序。

这个认知一旦建立，很多安全问题的答案就自动清楚了：权限校验放在哪里（宿主程序，不是提示词里）、怎么防止模型删库（不给它删库的工具）、模型被注入了怎么办（注入能让它请求危险操作，但执行与否由我们决定）。**安全边界永远在宿主，不在模型。**

**这一层引入的故障模式**：参数幻觉（调用了存在的工具但编造了参数值）、工具选择错误、无限重复调用同一个工具。

**对应我们的形态**：形态 D（流程自动化）用到这一层就够了——模型在个别节点做理解和抽取，流程本身写死。

---

# L4 · 标准化工具接入

**这一层解决什么**：L3 之后，每个 AI 应用要接每个业务系统，都得单独写一遍适配。十个应用接十个系统就是一百次对接。MCP 把这件事标准化：系统按标准暴露一次，所有应用都能用。

**书里对应的概念**：MCP（Model Context Protocol）、host-client-server 架构、tools/resources/prompts、工具注册中心、Schema 版本管理。

**要建立的关键认知**：这一层的价值是经济性，不是能力——有没有 MCP，模型能做的事是一样的，区别在于工具是一次性开发还是可复用资产。对我们这种要接贷款、采购、财务多个老系统的机构，这个决定的长期影响很大，值得在第一个 Agent 项目之前就定下来。

**这一层引入的故障模式**：工具描述写得不好导致模型选错（工具的 Schema 描述实际上是提示词的一部分，很多人没意识到）、版本变更导致下游应用静默失败、权限在协议层被绕过。

---

# L5 · Agent

**这一层解决什么**：前面所有层，都是"问一次答一次"。真实任务需要多步：查一下、根据结果决定下一步查什么、失败了换个方式、直到完成。这一步的跃迁不是模型变强了，而是**把决定下一步的权力，从我们代码里的 if-else 交给了模型在运行时决定**。

**书里对应的概念**：Runtime、ReAct、Plan-and-Execute、Reflexion、Self-Refine、记忆（短期/长期）、HITL、编排框架（LangGraph/AutoGen/CrewAI/Dify/Coze）。

**要建立的关键认知**：这一层带来的工程负担是断崖式的，而且和模型能力无关。因为路径不再可枚举，你就没法在上线前测完所有情况，于是必须补上一整套东西：状态持久化和断点恢复、超时与 token 预算上限、失败重试和幂等、每一步的审计留痕、人工介入点、评测集。

**原书说"平台"是从这一层开始才真正成立的，这个判断是对的**。L0 到 L4 都可以用应用级方案糊过去，到 L5 才必须有共享的运行时、工具治理、权限体系、可观测。

**这一层引入的故障模式**：绕圈子不收敛、跑偏（在错误的方向上执行很多步）、状态不一致（中途失败留下半完成的业务状态）、成本失控（一个任务几百次调用）、以及最麻烦的——**行为不可复现**，同样的输入两次跑出不同路径，出了问题很难归因。

**对应我们的形态**：形态 E。选型手册里给它设的四个前提条件（工具 15 个以内、单一业务域、失败可回滚、有明确完成判据），本质上都是在压缩"路径不可枚举"带来的风险。

---

# L6 · 多 Agent 协同

**这一层解决什么**：一个 Agent 的上下文和工具集装不下时，拆成多个各管一摊，再加个协调层。

**书里对应的概念**：A2A 协议、Agent Card；模式上有扇出并行、流水线、主管—工人、辩论、蜂群。

**要建立的关键认知**：这一层的问题不再是技术问题，是组织设计问题——谁监督谁、结论冲突听谁的、一个失败其余怎么收尾、整条决策链路怎么解释。而收益往往被高估：多数号称需要多 Agent 的需求，拆开看其实是 L3 或 L5 能解决的。

**这一层引入的故障模式**：协调开销超过并行收益、错误在 Agent 之间传播放大、成本成倍增长、故障归因几乎不可能。

**对应我们的形态**：形态 F。选型手册对它基本是劝退态度。

---

# 横切所有层的四件事

这四类不属于某一层，是每一层都要有的。原书把它们各自单列成部分讲，容易让人误以为是后期才需要的东西，实际上从第一个项目就要建。

**可观测**——OpenTelemetry、GenAI 语义约定、Langfuse/Phoenix。层数越高越关键，因为高层的行为不可复现，没有完整链路记录就无法排查。

**评测**——评测集、Ragas/DeepEval、LLM-as-Judge、各类基准。它决定你能不能判断"改了之后是变好还是变坏"。L2 以上没有评测集就不该上线。

**安全**——提示注入与间接注入、护栏、红队、OWASP LLM Top 10、NIST AI RMF、权限与身份传递。注意暴露面随层数增加：L2 引入了"消费外部文档"的注入风险，L3 引入了"能执行动作"的后果风险，L5 引入了"自己决定执行什么"的放大效应。

**成本与部署**——缓存（Prefix/Prompt/Semantic）、模型网关、路由、预算闸门、KServe、GitOps。成本随层数增长很快：L1 是一次调用，L5 一个任务可能是几百次。

# 两条重要的规律

## 一、越往上，模型的贡献越小

L0 层，系统能力基本等于模型能力。到 L5，模型只占整个系统复杂度的一小部分，剩下的全是状态管理、权限、幂等、审计、评测、成本控制这些传统工程问题。

这条规律的实际含义是：**换个更强的模型，对 L1、L2 的效果提升明显，对 L5 的项目成败影响有限。** 一个 Agent 项目失败，九成不是因为模型不够聪明。所以不要把预算和期望压在选模型上。

## 二、层与层的边界正在往下移

原本在应用层做的事，正在被吸进模型里。CoT 曾经是提示技巧，现在推理模型自己就会分步思考；多轮检索曾经要我们写循环，现在模型自己会决定再查一次。

这条规律的实际含义是：**架构上要让每一层可替换。** 今天你在 L2 写的检索循环，明年可能模型自带且做得更好；今天在 L5 写的一堆编排逻辑，明年可能大幅简化。所以不要把业务逻辑深度耦合进某个编排框架，接口留干净，以便到时候能把某一层直接摘掉。

具体做法可以借用一条运行时设计里的原则：**内部灵活、对外标准**。在系统内部用自己定义的数据结构承载业务语义（一次审查任务包含哪些要素、一个查询请求有哪些约束），只在与框架、模型、协议交界的地方做一层适配转换。判断做没做到，有个简单的检验：如果要换掉编排框架，需要改动的应该只有适配层，业务逻辑那部分代码不该动。反过来，如果业务对象里直接存的是某个框架的消息格式或状态对象，那就已经焊死了。

# 怎么用这份图谱

**判断需求落在哪一层**：需求只要一个答案，是 L1-L2；要它自己动手做几步，是 L5。层数决定工程量，也决定该给业务方报什么工期。跨一层，工作量通常翻数倍，不是加一点。

**判断团队该学什么**：正在做哪一层，就深入那一层加下面一层，上面的了解概念即可。

**判断供应商说的是哪一层**：这个用途很实际。销售演示的往往是 L5 的效果，但报价和实施范围是 L2 的。用这张图追问一句"这个功能落在哪一层、上面那几层谁来建"，能问出很多东西。
