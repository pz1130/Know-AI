# 上线与运维清单

> 配套《AI 需求技术选型手册》第四章底线（尤其"版本与回滚""全链路追踪""成本闸门"）和《概念讲解手册》第 8 讲（可观测与追踪）、第 9 讲（评测集）、"模型版本漂移"。手册讲"上线前必须有什么"，本清单补"上线那天和上线以后怎么做"。适用于形态 A–F，形态越靠后（E、F）越要全做。

---

# 一、上线前门槛（逐项打勾，缺一不上）

- [ ] 版本清单冻结：模型（精确到供应商版本号或快照名，不写"最新"）、提示词版本、工具 Schema 版本、检索索引版本、评测集版本，五项写进发布单。
- [ ] 评测集基线：在冻结版本上跑完评测集，记下分数作为回滚判据的基准。
- [ ] 追踪就绪：按 OTel GenAI 约定输出 span，能按发布版本筛选链路（见第 8 讲）；内容采集已按系统密级审批。
- [ ] 成本闸门已配置：单请求、单会话、每日三级上限与告警接收人。
- [ ] 回滚路径演练过：至少在预发环境真回滚一次，记下耗时。
- [ ] 人工兜底：系统关停时业务怎么继续（形态 D 退回人工处理队列；形态 A/B 显示"暂停服务"而不是报错页）。
- [ ] 4.2 硬约束复核：密级过滤、数据出境、问责留痕、结论性判定禁区、对外发布隔断，评审签字。
- [ ] 值班与升级路径：谁接告警、多久响应、什么情况下叫业务方和信息安全。

# 二、灰度发布

**原则**：AI 系统的"正确"是统计意义上的，小流量看不出问题时才放量；每一档都要有明确的放量和回退判据，不靠感觉。

| 阶段 | 流量 / 范围 | 停留时长（建议） | 放量判据 | 立即回退判据 |
|---|---|---|---|---|
| 0 影子运行 | 复制真实请求，结果不给用户看 | 3–5 个工作日 | 与基线 / 人工结果对比的准确率不低于评测基线 | — |
| 1 内部试用 | 项目组 + 种子用户 | 1 周 | 用户反馈与抽检无严重错误 | 出现密级泄露、越权动作、对外数字错误任一次 |
| 2 小比例 | 5%–10% 用户或一个业务局 | 1–2 周 | 抽检准确率、点踩率、成本、P95 延迟均在阈值内 | 同上；或关键指标较基线恶化超阈值 |
| 3 扩大 | 50% | 1 周 | 同上 | 同上 |
| 4 全量 | 100% | — | — | 同上 |

- **形态 D、E、F 会写业务数据**：灰度按"动作"而不是只按"用户"切：先只读、再写低风险对象、最后写全部；写入一律走幂等键（第 4 讲）。
- **按版本标记链路**：每条 trace 带发布版本号，才能把指标拆成"新版本 vs 旧版本"对比。
- **同时只变一样**：换模型、改提示词、改检索不要同一批上，否则回退时说不清是哪个引起的。

# 三、回滚

- **回滚单位是那五项版本组合**，不是单独某个文件。发布单里记"上一个已知良好组合"，回滚 = 切回那一组。
- **配置化切换**：模型名、提示词版本通过配置中心或网关路由切换，不需要重新发版；目标是几分钟内完成。
- **模型被供应商下线时**无法回到旧版本，提前登记各模型的停用日期，停用前完成新版本评测与切换（见第四节）。
- **业务数据的回滚**：形态 D/E/F 已执行的写操作不会因为切回旧版本而撤销，要靠补偿事务（第 4 讲）；回滚手册里必须写明"已写入的数据怎么查、怎么补偿、谁来确认"。
- **索引回滚**：检索索引保留上一版快照；重建索引期间新旧并存，切换后旧版至少保留一个发布周期。

# 四、模型版本漂移监控

《概念讲解手册》"模型版本漂移"一节指出：供应商会更新版本，效果可能变化且不一定通知。监控分三类信号：

**1. 版本信号（硬）**
- 记录请求的模型（`gen_ai.request.model`）和响应实际返回的模型（`gen_ai.response.model`）；两者不一致或响应模型名变化即告警。属性名以 OTel GenAI 约定为准，当前仍是 Development 状态，名字可能变（见第 8 讲）。
- 关注供应商的版本公告与停用日程，按季度登记到运维台账。

**2. 质量信号（软，需定期跑）**
- **定时回归**：每周用固定评测集跑一次线上同配置，分数与上线基线比；下降超阈值（如 3–5 个百分点，按业务定）告警。
- **线上抽检**：每周按比例抽样，人工或 LLM-as-Judge 打分（第 9 讲），分数挂到对应 trace（OTel 事件 `gen_ai.evaluation.result`）。
- **用户反馈**：点踩率、人工改写率（形态 C）、人工驳回率（形态 D 的确认节点）的周环比。

**3. 行为信号（间接）**
- 输出长度分布、拒答率、工具调用次数（`gen_ai.invoke_agent.tool_calls`）、平均步数、token 用量（`gen_ai.usage.*`）的分布突变。这些变化常常早于质量下降被看到。

**处置**：任一硬信号或质量信号告警 → 冻结该系统的其他变更 → 跑完整评测 → 决定回滚、调提示词或接受新版本，并更新基线。

# 五、事故分级与响应

| 级别 | 示例 | 响应 |
|---|---|---|
| P1 | 保密内容泄露给无权用户；AI 输出进入对外材料；越权写业务数据；成本闸门失效导致失控 | 立即停服或切人工；通知信息安全与业务负责人；24 小时内初报 |
| P2 | 关键数字口径错误被业务引用；Agent 写入错误数据但可补偿；大面积不可用 | 当日回滚或降级；补偿数据；一周内复盘 |
| P3 | 个别答案错误、延迟超标、点踩率上升 | 记录、纳入评测集、按迭代修复 |

**每次 P1/P2 都要把触发样本加进评测集**，防止同一错误再次发生。

# 六、事故复盘模板

```markdown

- 级别：P1 / P2 / P3
- 系统与形态：<系统名>，形态 <A–F>

- 发现方式：告警 / 用户反馈 / 抽检 / 审计
- 影响范围：涉及用户数、请求数、是否涉及密级内容、是否写入业务数据、是否进入对外材料

## 当时的版本组合
- 模型（请求 / 实际响应）：
- 提示词版本 / 工具 Schema 版本 / 索引版本 / 评测集版本：

## 时间线

## 根因
（不写"模型幻觉"了事；要写清楚哪道防线为什么没挡住）
```
