# Agent 平台落地与 AI 成本治理：会议要点

> 这篇是一次行业交流会的整理稿，按 KYA 的口径重新编排过。它不是标准，也不是厂商报价，多数结论是与会者的经验判断，所以文中凡是"会议观点"都只代表会上的说法；能找到官方出处的数字给了链接，找不到的标「待核实」。
>
> 和其他文档的关系：架构分层对应《概念层级图谱》L0–L6 和《协议对照表》；成本部分是《成本与容量估算》的管理层补充，那篇讲怎么算，这篇讲怎么管；护栏部分对应《AI 需求技术选型手册》第四章成本闸门和《上线与运维清单》。

# 一、Agent 用在哪，难在哪

## 1.1 目前跑得比较顺的场景

会上点名的成熟场景有五类：软件工程（异步写代码、测试自动化、DevOps/SRE、事件管理和根因分析）、网络安全（事件分析、自动响应、漏洞修复）、客户服务（文字和语音客服、问题分流）、数字办公助理（检索、总结、写文档）、财务和 HR 后台（应收应付、单据处理、入职、候选人筛选）。

共同点是流程相对标准、重复多、结果好衡量。放到我们行里，提款申请的单据核对、IT 值班的告警分诊，都比"帮信贷官做投资决策"更适合先上。安全类 Agent 是例外：场景成熟，但权限、运行时监控和人工介入要比别的场景严一档。

## 1.2 失败的项目，多数不是输在模型

会议观点：很多 Agent 项目效果差，不是模型不够强，而是没把数据和上下文给到位。具体是数据不准或不及时、业务定义说不清、来源追溯不了、工具和权限没配齐、工作流设计得别扭、上线前没好好评测。

会上把 Agent 需要的上下文分成三类。第一类是语义上下文：业务术语、规则、数据归属和政策，比如"项目停滞"在我们行到底指什么。第二类是实时业务状态：实时数据、检索结果，也就是推理那一刻要查的东西。第三类是溯源信息：数据从哪来、进了哪些流程、能不能审计。三类缺一类，Agent 都会一本正经地答错。

# 二、平台分层与解耦

## 2.1 六层结构

会上给的平台分层，从下往上是：

| 层 | 管什么 | KYA 对应 |
|---|---|---|
| 模型层 | 大/小模型、开放权重或闭源、多模态 | 图谱 L0–L1 |
| 集成层 | 通过 MCP 等开放协议接应用、数据库、工具、外部服务 | 图谱 L3–L4，协议对照表 MCP |
| 上下文层 | 把对的业务数据和知识送进来 | 图谱 L2（上下文供给） |
| 编排与运行时层 | 多 Agent 协同、工作流、状态、异常处理 | 图谱 L5–L6，A2A |
| Harness 控制层 | 工具/函数调用、身份、权限、记忆、运行时控制 | 图谱 L5 的循环控制，定义修订提案的设计旋钮 |
| 治理层 | 隐私、身份与访问、运行时安全、行为监控、Kill Switch、审计、成本 | 运维清单、选型手册第四章 |

会议观点：模型层和集成层正在标准化、商品化，企业真正拉开差距的是上下文层和治理层。这跟我们选型手册的判断一致：钱和人应该花在数据接入和护栏上，而不是自己训模型。

## 2.2 为什么要解耦

模型半年换一代，谁也不知道明年哪家最合适。会上建议把模型、Harness、编排、治理、数据与上下文、基础设施拆开，做到：换模型不用重写 Agent，治理层不跟某个模型绑死，上下文能力能被多个 Agent 复用。

对跨区域业务尤其要紧。会议举的例子是中国开发的 Agent 出海：境内境外用不同模型，控制平面和治理层保持一套，扩区域时只换模型层和基础设施。放到多边开发银行，就是总部和区域办公室可以跑不同的模型（数据不出境的地方用自建），但审批规则、审计口径和权限模型是同一套。

## 2.3 开放权重模型：灵活，但要算维护账

好处是能微调、能部署在云上、本地或边缘，按数据敏感度选地方放，也能减少锁定。代价是许可条款复杂、选型评测工作量大、补丁和升级自己管、运维成本高。会上还提了一个容易忽略的风险：所谓"开放社区"可能实际上靠一家厂商养着，厂商不维护了，生态会很快萎缩。所以选开放权重模型，除了看评测分，还要看维护方是谁、发版节奏、许可证能不能商用。

## 2.4 供应商的五种出身

| 类型 | 长处 | 短处 |
|---|---|---|
| 前沿模型实验室 | 模型迭代快，推理、电脑操作、工具调用强 | 企业集成、SLA、生态可能不足 |
| 云服务商 | 从基础设施到模型一条龙，企业服务经验多 | 技术栈封闭，容易被云锁定 |
| SaaS 厂商 | 懂具体业务流程 | 方案窄，按席位计价不适合 Agent |
| 自动化/RPA 厂商 | 流程治理、规则引擎、执行管理 | 对业务上下文理解弱，创新偏慢 |
| 数据平台厂商 | 手握企业数据和分析平台 | Agent 能力还在长，边界待观察 |

评估时别只看演示效果，要问清楚六件事：支不支持开放标准和 MCP、底层模型能不能换、能不能多云和混合部署、安全治理够不够企业级、可观测性全不全、成本能不能按项目看清。

# 三、自主性与护栏

会议的倾向很明确：自主性和护栏二选一时，先保护栏。先把护栏搭好，再一点点放权。

护栏清单：最小权限、限时访问、工具白名单、单任务 token 和成本上限、人工审批节点、运行时监控、异常行为检测、Kill Switch。改代码、付款、对客户做承诺、动生产系统这四类操作，要按最严一档管。拿支付停滞排查 Agent 举例：它可以查交易状态、拉日志、写诊断报告，但重发支付指令必须有人点确认。

## 3.1 全生命周期管理

Agent 多了以后，问题就不只是"怎么开发"，而是：有哪些 Agent（发现和登记）、好不好用（评估测试）、跑得怎样（可观测和监控）、能碰什么（权限）、是哪个版本、出问题怎么处理、什么时候下线、做没做过红队测试。会议观点：目前没有一个工具能覆盖从创建到退出的全过程；有大型企业内部已经跑着数万乃至数十万个 Agent（待核实，会上未给出处）。Agent 治理最后会像应用治理、身份治理一样，变成常规的企业管理问题。

## 3.2 业务人员自己用 AI 写工具

业务人员用 Codex、低代码这类工具自己做小程序，会上建议管四类风险。数据风险：走 AI 网关、敏感信息过滤和脱敏、和供应商约定数据不用于训练。安全风险：防提示词注入、限制外部访问、工具白名单、对外暴露的 Agent 做安全测试。质量风险：查幻觉和偏见、人工复核、对结果做测试。代码合规风险：追踪代码来源、识别开源许可证、走代码审查和发布流程，把这些工具纳入应用台账。

# 四、AI 成本怎么管（FinOps）

## 4.1 为什么越来越难估

模型多、价格差得大、输入输出分开计价，Agent 还会自己连环调模型和工具；SaaS 正从按席位改成按用量或结果收费；用的人不掏钱，也看不到自己花了多少。会议观点：推理成本会比训练成本更持续、更显著，AI 项目超预算的概率不低。

## 4.2 十条做法

1. 模型分层。金牌（最强最贵）、银牌（性价比）、铜牌（简单重复活）。银牌能干的不用金牌，铜牌能干的不用银牌。
2. 模型路由。按提示词内容、任务复杂度、用户身份、延迟和质量要求、成本限制、数据敏感等级自动选模型，企业策略可以覆盖自动判断。例如普通文档整理走便宜模型，涉敏数据只能走指定的自建模型。
3. 缓存。相同或相近的请求直接复用结果，可以用供应商的提示词缓存，也可以在企业 AI 网关里做。计费口径见《成本与容量估算》1.2 的 `P_cache`。
4. 给 Agent 设上限。单任务成本、token、执行步数、工具调用次数、运行时长和中止条件都要有。算例 E 里 8 步变 30 步，成本涨约 8 倍，这就是不设上限的后果。
5. 任务目标要封闭。说清楚做什么、输出什么格式、能用哪些工具、边界在哪、何时停、何时找人。任务越开放，Agent 越会烧 token 去试路。
6. 选对部署方式。公有云、私有云、本地、边缘、混合各有账。自建要算基础设施、人力、硬件折旧、闲置率和弹性；会上建议争取"基础容量 + 弹性容量"的运营费模式，别一次性囤卡。
7. 上下文保持精简。只给完成任务必需的信息，抽关键字段，不整份文档塞进去，删掉模型本来就懂的通用知识，限制检索条数，定期清理过期内容。上下文越长，越贵、越慢、越容易答偏。
8. 计价方式跟场景匹配。见下表。
9. 建 FinOps 工具。至少要能按人、团队、项目、模型看 token 和成本（可视化），能设硬上限（额度控制），能把成本展示或分摊到部门（Showback/Chargeback），能按历史趋势做预测。数据源可以直接用 OTel 的 `gen_ai.usage.*`。
10. 培训里讲成本。除了怎么用、怎么安全用，还要讲模型价差、token 和上下文怎么影响成本、缓存和批处理的好处、什么时候该用大模型。会上提到有企业要求员工通过 AI FinOps 培训和考试才能用 AI 工程工具。

| 场景 | 建议计价方式 |
|---|---|
| 重复性文档处理 | 按文档数或任务量 |
| 应收应付 | 按单据量或自动化流程量 |
| 客户服务 | 按结果、准确率、满意度或解决率 |
| 软件工程 | 按用户、Agent 或工作量 |
| 法务等专业场景 | 按用户、任务、结果组合 |

## 4.3 实时还是批处理

不是所有活都要秒回。候选人筛选、现金流分析、批量单据处理、数据清洗、报表生成、非紧急分类都可以走批处理。会上说批处理在某些情况下能省约 50%。这个数有官方出处：OpenAI 的 [Batch API](https://platform.openai.com/docs/guides/batch) 和 Anthropic 的 [Message Batches](https://docs.anthropic.com/en/docs/build-with-claude/batch-processing) 都标明比同步调用便宜 50%，但其他供应商和自建部署不一定，按实际报价为准。月末的提款单据核对就是典型的批处理场景。

## 4.4 成本跟责任要对上

技术手段只能解决一半，另一半是"用的人不付钱"。会上给的办法：每人或每团队有默认额度，超额时显示额外成本，要追加额度就说明业务价值，由产品负责人或业务负责人审批，高回报场景给高额度。一句话：谁用谁关注，谁要追加谁说明价值。

IT 人员嫌低阶模型不好用怎么办？会议观点：高等级模型不是不能用，但要有清楚、可验证的理由，配合上面的额度、路由和分层一起管。

## 4.5 先放开还是先控

看阶段。探索期可以适度放开，先弄清楚员工愿不愿用、哪些场景值钱。进入规模化，就得补上路由、额度、FinOps 可视化、价值评估、预算审批和部门分摊。"员工用上了 AI"不等于"企业完成了 AI 转型"，最后要看组织层面的效率和业务结果。个人省下的时间不会自动变成组织产出。

## 4.6 预算怎么拆

预算不能只看模型单价。成本项至少包括：模型调用、Agent 执行和工具调用、数据和向量库存储、AI 网关和平台、监控治理、算力、开发运维人力、安全合规审计、许可订阅。

估算步骤：明确用例和目标 → 拆工作流 → 拆成任务 → 每个任务定大/中/小模型 → 估调用频次和 token → 区分实时和批处理 → 比较不同模型和部署方式 → 加上增长、峰值和异常 → 用 POC 拿真实数据 → 按月或按季修正。具体公式和算例见《成本与容量估算》第一到三章。会议观点：模型单价总体在降，预算失真主要来自 token 用量、Agent 调用次数和 SaaS 计价方式的变化。

# 五、建设路线：自研还是外购

看两件事：自己的工程和平台成熟度，以及想掌握多少 Agent 底层能力。核心业务流程、核心数据和上下文能力、治理与权限体系、长期要掌控的差异化能力，适合自研；通用办公助理、通用财务 HR 工具、标准后台流程、自己没能力长期维护的底层组件，适合外购。会上建议的模式是"核心自研、通用采购、平台组合"，别全自研也别全外包，更别盲目上重资产的模型和算力。

SaaS 厂商在 Agent 化，会上提醒企业 IT 关注：传统界面可能被 Agent 交互取代，计价可能从席位转向 token 或结果，要看厂商是否支持开放标准、是否允许换模型和 Agent、有没有锁定风险。

Private AI 方面，会议观点是中国关注度较高，美国过去一年也在上升（待核实，会上未给数据）。推动因素：小模型和开放权重模型成熟了，把 AI 搬到数据旁边通常比把数据搬上云便宜，强监管行业和数据主权要求更强的控制。对我们这类机构，它首先是合规和数据安全问题，其次才是技术选择。

AI 转型也会动组织：招聘、培训、绩效、IT 与业务边界、外包与内制。会上建议 HR 管组织变革和员工接受度、CFO 管价值和成本、CIO/CDO 管架构平台和治理、业务部门负责把 AI 变成业务结果。

# 六、会议共识（摘录）

1. 难点不在模型，在数据、上下文、治理和组织变革。
2. 优先建模型中立、平台解耦、支持开放标准的架构。
3. Agent 治理要覆盖发现、评估、运行、监控、权限、安全和退出全过程。
4. 模型分层、路由、缓存、批处理、token 限额、精简上下文是控成本的主要技术手段。
5. FinOps 要做到可视化、额度控制、成本分摊和趋势预测，不能只由 IT 扛，财务、业务、HR 都要参与。
6. 自研聚焦差异化能力；培训要讲成本意识和模型选择。
7. 目标不是用更多 token，而是用可控的成本换可衡量的业务价值。
